# Multi-Agent Evidence Controls

Parallel agents increase throughput only when mutable resources and evidence are isolated. Treat model reports as untrusted proposals until Main-Hermes reproduces them.

## Procedure

1. **Inventory before dispatch.** Record the canonical repository and revision, existing worktrees, active writers/processes, test databases/schemas, generated dependency trees, and release target. Assign exactly one owner to every mutable resource.

2. **Build a resource-safe graph.** For the operator's multiple independent requests, dispatch separate agents by default rather than serializing all work through the parent. Keep a task/owner/output-path ledger and deliver one consolidated, verified update. Parallelize source reading, independent reasoning, and immutable evidence collection; serialize true dependencies and shared writes. Give each writer a separate worktree. Make test execution a serialized node unless every lane has a unique database/schema, cache, queue, filesystem output directory, and dependency install.

3. **Enforce permissions structurally.** Task-body phrases such as “read-only” are not enforcement. Reviewers should receive a non-writing toolset or a disposable copy rather than the canonical repository. Give only the named writer write-capable tools and verify the repository stayed unchanged afterward.

4. **Bind restricted evidence before execution.** For a private source or financial-data lane, require a sealed entrypoint, exact task ID, target allowlist, fields, byte ranges, current source digests, purpose, and approval artifact before content is read. Split comparison pairs into small explicit batches. A count/hash coverage ledger proves retrieval only; it does not prove semantic equivalence or a correct retain/port/omit decision.

5. **Make approval artifacts meaningful.** A self-authored approval, placeholder seal digest, or producer-PID inequality is not independent authorization. Bind approval to the exact task, preparation digest, current seal, time window, and target allowlist; keep it outside the consuming process's writable root or verify it through an inaccessible signing/keychain-backed authority. For a host-owned immutable-file boundary, require a fixed policy file in a host-only directory (0700 directory, 0400 immutable regular file), a host-only issuer that runs after the exact preparation exists, and an authorization file that is external to the private run root, bound to policy digest plus exact preparation/seal, time-bounded, and single-use via exclusive creation. Preserve expired and consumed authority files as evidence; issue a fresh nonce/policy revision rather than deleting or reusing them. Test stale, mismatched, self-issued, broadened, replayed, expired, and alternate-name approvals deny before private input is consumed.

6. **Isolate stateful tests.** Allocate a unique database/schema name per lane and verify it before any migration, `migrate:fresh`, `RefreshDatabase`, fixture load, queue run, or cache clear. If unique state cannot be allocated, run those tests serially after all other agents stop. Never share mutable `vendor/`, `node_modules/`, virtualenvs, framework caches, or generated loaders across worktrees.

5. **Keep secrets out of fan-out.** Never place credentials, tokens, employee/student PII, or payment data in agent bodies, comments, artifacts, or model context. If a key is pasted into chat, do not forward or store it; use the profile's existing secret reference and tell the user to rotate the exposed key.

6. **Recover budget-exhausted lanes before redispatch.** When a worker times out, read its transcript and inspect the assigned worktree, branch tip, diff, untracked files, and commit graph before starting a replacement. For research lanes, inventory saved source extracts, workbook snapshots, calculation scripts and reports instead of assuming a repository exists. Verify claimed files still exist and inspect their substance: a report containing only headings and PENDING placeholders proves preparation, not completed research, and a promise to write a model is not a model. Continue a coherent artifact with a narrowly bounded, artifact-first task; if none survives, close discovery and reassign only the concrete missing deliverable. Perform mechanical extraction, distinct-state counts, joins and arithmetic directly in code rather than redispatching broad research lanes to read the same large tables. Check underlying document generation dates and actual row coverage; downloaded-file timestamps and overview totals do not establish fresh or complete evidence. For a reproduced, mechanical fix, apply the bounded edit and run the canonical tests rather than launching another broad discovery loop. A timed-out reviewer waiting for a future candidate is `NOT YET PROVEN`, not a failed review or a reason to review the rejected baseline again. A second failure mode is step-budget exhaustion: the lane exits 0 with a sub-1KB log saying it ran out of turns before producing the deliverable — the log exists and looks like an artifact, but the JSON verdicts are absent. Probe every lane's log for substantive content (size + parse) before consuming it, and never count a stub as a completed seat. When a lane fails, retry once with a higher step budget/output ceiling (scale `--max-turns` and run budget with expected output size); if it still fails, proceed with the surviving lanes, document the gap in the ledger/receipt, and report the effective reviewer count honestly. If the parent completes the missing analysis, report it as parent-verified work; do not label it an independent completed swarm review.

7. **Reconcile after every fan-out.** Wait for or stop all relevant workers, then inspect the canonical repository and every writer worktree:

   ```bash
   git status --short
   git worktree list --porcelain
   git diff --stat
   hermes kanban show <task-id> --json
   ```

   Enumerate every created file and commit. Do not accept a worker's `changed_files`, PASS count, root-cause statement, or “no edits” claim without this readback.

9. **Re-run objective checks from a clean state.** Before accepting an adapter's mocked suite, inspect the existing trusted client and an observed response or authoritative provider schema. Test the real request/response shapes, question IDs, headers, errors and usage fields; make the fake reject the wrong shape rather than reproduce the implementer's assumption. Require a discriminating negative test and separately label any authorized live smoke. Matching invented mocks can produce a green suite for an API that will reject every real request. Main-Hermes runs the canonical test command serially after resetting only the explicitly named test database/schema. Record the exact command, revision, database/schema identifier, and output. A test that passes immediately is regression coverage, not RED evidence.

**File-editing fan-out (content repair, doc/table fixes):**
- **Use completion-driven execution.** Run an independently owned long-lived orchestrator as a background process with completion notification and checkpointed manifests. For runtime-managed delegations, consume delivered completion results rather than polling transcripts or artifacts to wait. After completion, inspect each assigned artifact for substantive content; process exit alone does not establish a usable deliverable.
- **Per-writer machine-readable manifest.** Each writer must write a JSON array — one entry per changed item: `{ref, field, action, old_start, new_start, grounded: bool, source}`. The manifest is the reconciliation input; `grounded=false` entries route to a human/verification list instead of being accepted.
- **Guardrail diff gate against a pre-snapshot** (git HEAD or saved checksums), not just "agent said done": the columns that must not change (e.g. a status column, an approach/evidence column) compared as multisets, zero row loss, zero unparseable table lines, and the derived downstream count (e.g. built NOT-COMPLIANT total) matching expectation. A mismatch almost always traces to one writer corrupting structure (merged cells, dropped delimiters) — inspect that writer's file diff before any rebuild.
- **Daisy-chain option:** when the review needs a running cumulative state (tallies, carried-forward findings), run review agents sequentially and make each read the previous report and carry its verdict forward; parallel is for disjoint work only.
- **Never let a writer run the rebuild/verify step** — writers edit their assigned files and emit manifests; the deterministic rebuild + guardrail diff + downstream sync run once, by Main-Hermes, after all writers finish.

10. **Test stateful security protocols with a complete effect census.** For admission, replay, fencing, recovery, transaction, and crash tests, assert more than the response status: record authority/control state, append-log rows by kind, witness receipt status and dispatch-spent state, domain row versions, audit/outbox counts, and prepare/claim/finish/callback counters. A safe error can coexist with a consumed assertion or an incorrectly terminalized committed action, so status-only tests mask protocol defects.

11. **Make test mutants falsifiable at the intended boundary.** Run top-level transaction, retry, crash, migration, and concurrency tests without a framework-owned outer transaction; assert transaction depth before and after the subject. Mutate one guard or invariant at a time in a disposable fixture, restore every other guard byte-for-byte, and require the paired test to fail on its intended behavioral assertion rather than bootstrap, syntax, or a different missing guard.

12. **Represent shared protocol state faithfully in concurrency tests.** Use independent processes and connections plus explicit barriers at lock, prepare, claim, and commit. Put any test witness state in a unique scratch path outside the repository and verify it is shared atomically; separate in-memory doubles cannot prove cross-process ownership. If the required shared test resource is unavailable, mark the concurrency result NOT YET PROVEN.

13. **Reconcile test ledgers mechanically.** Wire every newly added regression module into the repository's actual CI entrypoint before final verification; explicit module lists can omit files that pass when run individually. After writers stop, run the integrated suite against one stable candidate. When stronger controls invalidate older fixtures, preserve the denial assertion and build the positive fixture through the real prerequisite workflow—for example, execute and verify a parent before accepting its dependency instead of inserting an acceptance flag. Parse each suite log and report exact suite count, executed, passed, failed, and errored totals. Retain stale fixtures or pre-existing failures as explicit historical evidence; never label them green, exclude them from denominators, or silently reinterpret them. When a checker fails, prove whether the artifact violates its contract or the checker misparsed a nested structure or overmatched a harmless identifier; preserve the original failing result either way.

8. **Invalidate contaminated evidence immediately.** If parallel lanes touched one database, schema, generated dependency tree, cache, queue, or output directory, treat all affected results as invalid. Stop the lanes, restore a clean isolated state, and rerun serially. Drop/migration races can manufacture false failures, false passes, and false root-cause claims.

9. **Correct durable records, not just prose.** When a Kanban completion is misleading, preserve the original audit trail but replace the active result/summary and attach structured invalidation metadata:

   ```bash
   hermes kanban edit <task-id> \
     --result "INVALIDATED: <objective reason>" \
     --summary "INVALIDATED: <decision-relevant reason>" \
     --metadata '{"release_evidence":false,"reason":"<cause>"}'
   ```

   A later comment alone does not neutralize a misleading completion summary.

10. **Quarantine unsupported artifacts.** Move unauthorized or unsupported untracked files outside the repository into a clearly named evidence quarantine. Add a README stating what is valid, what is unsupported, and that the files must not be merged, published, deployed, or cited as release evidence. Recheck `git status --short` afterward.

14. **Validate feature disposition semantically.** Do not label a feature absent merely because its source digest differs. Before porting a same-name or same-purpose candidate, perform a source-grounded functional comparison and classify it as equivalent, complementary, distinct, or NOT YET PROVEN. A byte-identical pair may support duplicate omission; non-identical pairs need semantic evidence. Ensure the matrix says “no byte-identical peer,” not “absent,” until semantic comparison establishes actual absence. Keep the destination feature until a replacement/merge decision is proven.

15. **Adjudicate review claims at the actual control-flow and framework boundaries before rewriting.** Reproduce a claimed state-machine defect with the exact prior state, input transition, clock, and branch predicate; even a high-severity independent finding may reverse a condition and prescribe a harmful fix. For freshness tests, explicitly set both the injected clock and fixture timestamp, and exercise fresh and stale cases separately—a stale-only test cannot catch improper trust in a fresh self-reported status. Keep confirmed defects and disproved allegations in separate adjudication entries, preserving the original review and the reproduction result. Inspect the installed framework version, serializer/hydrator, binding configuration, and request integrity checks before accepting claims that a public model property exposes all attributes or permits identifier replacement. Bind the reviewer packet to those dependency sources as well as application code; omitted framework behavior can reverse the finding. Require a real rendered snapshot with distinct secret canaries and request-boundary tests for nested property changes, top-level model replacement, and signed-metadata tampering. Test ownership/enrollment revocation between initial mount and a subsequent action separately: identifier integrity does not prove continuing authorization. Distinguish initial render, hard reload, and asynchronous component morphing when investigating stale UI state. Record each allegation as reproduced, source-refuted with coverage limits, or NOT YET PROVEN; a generated reproduction recipe is not execution evidence.

16. **Gate root cause and release separately.** Static code reading may rank hypotheses but cannot prove a production cause. Require the exception/event or a faithful isolated reproducer, RED→GREEN evidence, independent review, exact revision approval, deployment readback, and live acceptance before declaring completion.

## Uncoordinated duplicate sessions (resumed CLI sessions in one live worktree)

The planned fan-out above is controlled by a dispatch graph. A second failure mode has no graph at all: the same user resumes several stale CLI sessions (a "continue" re-enters a session that re-discovers the same in-flight work), and multiple foreground agents start editing the same live worktree simultaneously. Detect it and self-coordinate — there is no owner assignment:

- **Signs:** files appearing or vanishing between your turns, the git index mtime advancing without your writes, unexplained untracked probe/scratch files, `git reflog` showing resets you did not run, and `ps aux | grep 'hermes --resume'` listing sibling sessions.
- **Read the siblings before editing:** search session history for the siblings' recent activity. At least one has usually already read the exact files you are about to edit, and one of them may be waiting on YOUR commit as a gatekeeper.
- **Claim one role:** writer (edits + the commit) or gatekeeper (watch file mtimes / HEAD, run the verification gate once the writer's commit lands, never edit concurrently). Two sessions both editing and committing the same worktree is the failure to prevent.
- **Re-read worktree state fresh immediately before committing** (status, log, HEAD): a sibling may have committed, reset, or deleted files after your last read. Stage only what you own, verify `git log` before and after your commit, and note the collaboration in the completion record so the board reflects who actually did the work.
- **If a sibling already rebased/pushed the shared branch, verify the rebase before building on it:** `git diff <pre-rebase-sha> <new-sha> --stat` should show only the upstream's files (your work preserved 1:1), check file overlap with the new upstream commits, and re-run the full suite on the new base before committing on top. A sibling rebase is untrusted input until those three checks pass.

## Option-based research and decision debates

- For the operator's complex capital/regulatory option reviews, produce substantive research plus separate editable Word briefs and Excel models for each outcome, with a consolidated recommendation and comparison index. Each brief should explain the mechanism, financial consequences, student/customer obligations, legal prerequisites, execution owners, evidence gaps and decision-reversal conditions. Recalculate and exercise the workbooks; package verified files rather than delivering only a narrative or plan.
- When the operator requests five-agent groups for each option, use five genuinely independent agent tasks per team, not one agent simulating five voices. Useful seats are advocate, regulatory researcher, financial analyst, student/operations reviewer and skeptic. Maintain an actual dispatch/completion ledger; planned seats and timed-out workers are not completed participants.
- Before launch, enumerate opening seats, rebuttal representatives and final ballots separately, and size the complete review against concurrency and available runtime; an opening-round count understates a multi-round commitment. Treat requested worker deadlines as targets unless the runtime actually enforces them. Keep initial arguments independent, then circulate the same corrected evidence and finalist to all final voters.
- Resolve retrievable decision-critical inputs once in the parent before expanding advocacy; inspect the named source workbook cells, headers and adjustments rather than letting many agents debate a data gap that local evidence can close. Read the complete operative rule, including alternative/deemed-compliance paths, exceptions and cross-references, before converting a baseline test into a hard gate. Preserve separate eligibility branches and their AND/OR conditions; repeating an incomplete summary across agents does not establish the governing requirement. Version material discoveries and circulate them to every rebuttal participant and final voter; distinguish missing current certification from available historical book evidence.
- For reasoning over already verified evidence, allow each actual agent to return compact structured JSON for parent archival instead of repeating source discovery and file-writing work. Put the complete output schema in the initial dispatch; do not rely on later steering to repair it. Label parent-archived returns and supplied source excerpts honestly, without implying fresh independent research or a child-written file.
- Adjudicate facts before aggregating scores: read each completed artifact, recompute financial claims, and check its citations against the source's scope and wording. Preserve the original argument, publish a separately versioned correction sheet, and require rebuttals and final ballots to address it. Distinguish a completed argument from accepted factual claims; an advocate may submit a substantive artifact containing disqualifying errors.
- Conduct evidence-based cross-examination, preserve the strongest opposing arguments, and require explicit acceptance, conditional acceptance or dissent on the same finalist and conditions. Do not manufacture unanimity or run indefinitely when missing facts prevent agreement. Distinguish spokesperson concessions from member votes and procedural hard constraints from proof those constraints are satisfied. Report the winner, why rivals lose, remaining dissent and facts that could reverse the decision. If compatible options win as a sequence, identify a combined plan rather than pretending it is one mutually exclusive option.
- Derive progress from the persisted seat ledger after checking every write result; unsuccessful batch patches must not advance dispatch or completion totals. Track unique seats, total attempts and failed attempts separately: a replacement completes the original logical seat and never creates another vote. For mass task graphs, track planned, created, claimed/running, completed, failed, and blocked counts separately—task creation is preparation, not deployment, and a provider-auth crash is zero completed evidence even when every card exists. Retain actual delegation IDs, artifact hashes, challenged claims and missing seats. Require all counted artifacts to contain substantive arguments, not merely valid JSON or headings. Gate each phase separately as prepared, dispatched and completed: validate generated packet keys and required fields before kickoff, and advance to dispatched only from an actual runtime acknowledgement. A completed opening round or prepared rebuttal packet does not mean cross-examination has started; an unlaunched phase has no completion callback to resume it. Report opening, rebuttal and ballot coverage separately rather than presenting one round's total as overall completion.
- For financial/legal debate checks and correction-sheet structure, use [Research-debate adjudication](references/research-debate-adjudication.md).
- When the operator changes the strategic recommendation, propagate the new position consistently through every current brief, model and investor-response draft while retaining superseded versions as history. Do not alter evidence to fit the recommendation. Separate enterprise financing from local-market continuation/exit: funding to satisfy remaining-state requirements may still be needed after a local exit, and a modeled current-ratio improvement is not proof that every legal, equity, reporting-period or lender requirement passes.

## High-volume independent review

- When the operator requests an exact reviewer count, deliver that many distinct substantive review contexts, not simulated voices. Verify unique seat IDs and provider generation/delegation IDs, report the models that actually returned accepted work, and keep coordination/synthesis separate from the requested reviewer count.
- Smoke-test one representative request per provider/model route with the real evidence size and output schema before expanding the queue. For Kanban fan-out, require both a direct one-shot auth/model smoke and one representative canary card that is claimed and returns a substantive completion with the intended skills and workspace; a configured profile or created card does not prove an executable worker. Inspect finish reason, usable final content and usage: reasoning can consume a combined output budget before JSON is complete. Change reasoning settings only after proving the endpoint accepts them; retry only failed seats through a tested, disclosed route.
- Preserve failed and interrupted attempts without overwriting their receipts. Treat unreturned provider usage as unknown and retain a conservative budget reservation; recorded response costs are not a complete invoice when requests were interrupted.
- Deliver a prioritized, source-adjudicated register separately from raw candidate findings. Count suggestions, verified defects and completed reviewers independently; a completed review is not an accepted factual claim.
- Match delayed completion notices to the task, process, candidate revision and phase in the execution ledger before reacting. Resume the next already-authorized dependency when evidence permits; do not ask the operator to resend a request merely because its background phase finished later. Do not rerun finished work or present an already-recovered startup failure as a current blocker. A packaging success proves packaging only, not installation, UI loading or a live connection; avoid repeated user-facing status messages when the verified result has not changed.

### Durable Kanban graph controls

- Store the binding contract and source manifests in a durable Kanban/project path or attach them to a parent card; do not make descendant execution depend only on a cache/scratch path that can be pruned while the graph is still running. Re-read the contract path from a canary worker before opening the fan-out.
- Smoke-test the **exact profile plus forced-skill set** on one representative card. A direct model reply proves authentication only; the real worker can still fail before reasoning because that profile does not have a named skill. Reassign or propagate skills before launching the batch, and preserve the failed canary as zero completed evidence.
- Recover only execution blockers whose cause is mechanical and reproduced (provider authentication, unavailable forced skill, dead worker, pruned contract). Never auto-unblock a semantic FAIL, an explicit human-input gate, or a safety refusal. Record the cause, reassign to a tested route, then verify the card is running rather than merely ready.
- When an exact-revision review returns FAIL, create a new single-writer repair card and fresh independent re-reviews; add those new cards as parents of synthesis and final approval immediately. A completed failed review satisfies dependency mechanics but never satisfies semantic acceptance.
- Keep package completion, release approval, and communication separate. A graph may finish with `NOT YET PROVEN`; in that state the package and manual-input register can be delivered locally, but publication, attachment drafts, and approval notifications remain blocked.
- Collapse unresolved evidence into two outputs: a complete machine register and a short decision packet grouped by person/field. Do not hand the operator hundreds of row-level questions when a few dated roster/reporting adjudications would resolve the same blockers.

## Always-On Rules


- One writer per branch, database/schema, generated dependency tree, and external record.
- Evidence over agent consensus; ten agents repeating one guess is still one unproven guess. Verify workflow execution state and job counts before accepting a code-failure diagnosis: `action_required` with zero jobs proves no jobs executed, not a failing test or defective patch. Repeated alerts do not strengthen missing evidence.
- Check review execution separately from authentication: a logged-in CLI or exited process does not prove a substantive review occurred. Require the reviewer verdict and exact artifact digest; a provider refusal produces NOT YET PROVEN, never approval. Preserve the failed attempt and use an authorized alternate reviewer without weakening independence or release gates.
- Validate orchestration order in addition to unit-test totals. If builders must critique evaluators before synthesis, assert those critiques exist before candidate construction and appear in every final reviewer packet; passing tests of a different sequence do not satisfy the contract.
- Use PASS / FAIL / NOT YET PROVEN. Never convert static plausibility into a live PASS.
- Test verification machinery adversarially before trusting its green suite: replace required gates or scope, use a truthy non-boolean verdict, supply a correctly hashed artifact containing unresolved work, and substitute a self-authored reviewer receipt. Reject any resulting PASS; hashing an artifact proves identity, not successful execution or independent approval. The approved contract and reviewer authority must come from a separately trusted input, not the certificate being checked.
- Verify generated agent configuration through the installed runtime's actual loader and resolved tool registry in a disposable home. Reading back the generator's own manifest cannot prove the runtime loaded it or denied tools. Distinguish configuration isolation from an OS sandbox, and an empty tool surface from a functioning domain workflow. Pair the safe profile with a deliberately unsafe disposable profile and require the checker to reject its effective tool exposure. Assert the mutation changed the intended configuration: adding a tool to an allowlist while leaving it disabled elsewhere is still a safe configuration, not a valid unsafe negative control. Verify the loader's effective home and exact config path rather than assuming a HOME environment override isolates profile discovery.
- Reproduce corrected Python behavior in a fresh subprocess from the exact candidate checkout and print the imported module's `__file__` when provenance is uncertain. Persistent execution kernels retain imported modules after source edits, so a probe can silently test the previous candidate.
- Scope disposable-home tests to child processes: construct a copied environment with temporary HOME/HERMES_HOME values and pass it to subprocess.run rather than exporting test paths into a persistent terminal. Verify the parent environment is unchanged after the test. Before diagnosing suddenly missing authentication, compare the effective HOME, HERMES_HOME, and credential-config directory with the intended operator context; a test-home leak can hide valid credentials without any credential failure.
- Preserve rollback sources and original audit events while correcting the active conclusion.
- If a required production artifact is inaccessible, request the narrowest access or redacted artifact and stop rather than shipping diagnostic guesses.
- Do not treat cache driver allowlists, sentinels, or successful atomic writes as evidence that security replay history survives selective eviction, restoration, or failover. Require an authoritative replay ledger with a tested monotonic generation and recovery fence; if that needs schema or infrastructure, return to the critical-contract gate rather than simulate durability in a cache.
- Stop a worker that drifts from a finite decision artifact into repeated inventory or index generation; require the stated matrix, verdict, or test package before opening another lane.

## Completion Check

- [ ] Canonical repository contains no unauthorized artifacts
- [ ] Every writer worktree and mutable test resource had one owner
- [ ] Stateful tests were isolated or rerun serially from a clean state
- [ ] Agent claims were reconciled against files, commits, commands, and external readback
- [ ] Contaminated Kanban results were actively invalidated
- [ ] Root cause and release gates are supported by reproducible evidence
