# Engineering Swarm — local execution binding

The `engineering-swarm` skill owns ROUTING (offline planner, policy). This skill is the EXECUTION binding on the operator's Mac: how to actually run a routed plan with git worktrees + `hermes -p <profile>` workers. Policy gates (+G, +H, cross-family, stop-at-commit) apply unchanged — this only says how the nodes run. See `templates/run-item.sh` for the proven chain runner.

## When to use
After `router.py` emits plans for code work in a local repo and the operator has approved the build.

## Procedure
1. Validate the package first: `python3 -m unittest discover -s <pkg> -p test_router.py` (expect OK) before trusting any plan.
2. Re-verify spec premises against the base. Task JSON is built from specs/briefs that can be days stale. Before dispatch, read/grep each item's premise against origin/main at the exact base SHA — the item may already be built on main (or fixed, or moved). Re-scope the task JSON to the actual gap and record what already exists. This is the highest-value 10 minutes of the build; a stale premise costs a whole rejected PR.
3. Task JSON per item: task_id, `base_revision` = FULL sha of origin/main, owned-file list, signals, `effort_hint: null`, `mode` = the operator's selection, limits, `opinions.stage2/stage3` as classifier stand-ins (note when the L-tier local classifier is unavailable).
4. Route each: `router.py <task>.json --mode <selected>`. Expect raises (floor, not ceiling): external-writes → hard; `seed*`/migration paths → T7 critical → expert with +G +H; no-repro bug → +P plus one effort-level raise. Log the raises; never lower to fit.
5. One git worktree per item, created from the exact base SHA (`git worktree add <dir> -b feat/<item> <sha>`) — never from a dirty checkout's branch. Items never share worktrees.
6. Write three briefs per item:
   - TD (test designer): independent test design, writes ONLY test files, designs from the CONTRACT not the current implementation; tests that encode the target state go red on current code.
   - IM (implementer): make TD's tests pass; may adjust only a test factually wrong about the contract and must report it; owned-file scope stated explicitly.
   - RV (cross-family reviewer): review diff+source (NOT the implementer report), run the tests itself, mutation spot-check 3 critical tests (break → RED → revert), scope/copy/kill-switch/tsc-delta checklist, ends with a single `VERDICT: PASS|FAIL` line; FAIL carries numbered findings with file:line + exact fix. A call-count assertion of the form `expect(buildIndex).toHaveBeenCalledTimes(1)` only has TEETH with ≥2 inputs: with a single input row, moving the call INSIDE the per-row loop still calls it exactly once and the test stays GREEN — a fake test that would let a per-item N-API-call regression ship silently. Require the count-1 test to stub a multi-row input and assert the per-item lookup ran once per row. This is the "mocks mask broken logic" failure the gate exists to catch, now in its most common shape. Sibling shape: a `mockReturnValueOnce`/`mockImplementationOnce` stub consumed by an EARLIER phase of the same call (e.g. a stamp phase before a re-check phase) leaves the later phase's `db.select` resolving `undefined`, which crashes into a catch and emits a string the assertion matches for the WRONG reason — the suite stays green while the guarded invariant is never exercised. The gate catches this only by its own mutation run, so the brief must require each phase's query to be stubbed separately (mirror the helper that stubs it per-phase) and require the discriminating mutation (mutate the source the test guards → must go RED → revert) as the test-design exit condition.
7. Dispatch: `hermes -p <profile> chat -q "$(cat brief.md)" --oneshot -Q --max-turns <N>` per node, chained TD→IM→RV per item in a shell script (use `templates/run-item.sh`), one script per item, launched as separate `terminal` background processes, width ≤ 4 disjoint owned-file sets.
8. Collect verdicts. FAIL-with-findings is a normal GOOD outcome — the gate exists to catch real bugs (it catches broken SQL that mocks mask, row-count guards that false-accept on retries, features wired in helpers but not at call sites, missing kill-switches, scope bleed). Never weaken the checklist to force a PASS.
9. Attempt 2 (failed items only): targeted fix brief quoting the reviewer's numbered findings verbatim; fixer and re-reviewer again different families; the re-reviewer verifies EACH finding resolved (cite file:line + its own test run) then re-runs the full checklist. Cap retries per policy.
10. STOP GATE in every brief: commit locally only (test + feat/fix commits); NEVER push, PR, or run prod migrations. Hand the operator per-item verdict + commit SHAs; his explicit approval gates push/PR/merge (merge auto-deploys on Vercel).

## Base reconciliation before fan-out (do this BEFORE step 5)
- Local `main` is usually stale and origin/main moves during a long session: re-resolve `BASE=$(git rev-parse origin/main)` in the SAME step that creates the worktrees, and verify the SHA you planned against (`git merge-base --is-ancestor <planned-sha> $BASE`) — a new base that is a descendant of the planned one is safe; a diverged one is not.
- A branch that is "done" locally may already be on main as a SQUASH merge: its commit SHAs fail `git merge-base --is-ancestor` against origin/main even though the work is live. Detect with `git log origin/main --oneline --grep '<pr-title-keyword>'` before assuming a branch still needs to be merged — and before assuming it DOESN'T (squash merges leave the old branch redundant but its uncommitted WIP possibly still needed).
- Uncommitted WIP in the checkout is never destroyed and never carried: `git switch -c wip/rescue-<date>`, `git add <the code files only>`, commit, then switch back. Untracked files block `git switch`/`checkout` ("Please move or remove them before you switch branches") — a fresh `git worktree add` sidesteps the block entirely, which is another reason to prefer worktrees over checking branches into the main checkout.
- A `git diff origin/<main>..HEAD` file list that grows by files absent from the branch's commits = the origin ref moved mid-verification (a fetch landed). Never read scope from a moving diff range — verify commit contents with `git show --name-only <sha>`.

## Multi-item sequencing (more than one item in one build)
- Disjoint owned-file sets run in parallel (width ≤ 4). Two items touching the same file either run serially or get LINE-LEVEL ownership split in the contracts (e.g. "you own the invite-sequencing lines; the other item owns the referrer-attribution lines of this same route") — the split must be named in both contracts.
- A dependent item builds on the MERGE of its prerequisites: merge the landed item branches into a chain branch (`git checkout -B feat/<build> $BASE; git merge --no-ff feat/<item-a>; git merge --no-ff feat/<item-b>`), then recreate the dependent's worktree from the chain head. Migration file numbers are coordinated across items in the contracts (0060/0061/0062…) so parallel items never collide in `drizzle/`.
- Seed each worktree's deps fast: `cp -Rc <main-checkout>/node_modules <worktree>/node_modules` (APFS clone-on-write — seconds, not the 2–5 minutes of `npm install`). `cp .env.local` too — worktrees start without gitignored files.
- Verify a PASS before integrating: re-run the item's own vitest set + `next build` in its worktree before merging it into the chain branch. The reviewer's VERDICT is a self-report; a 2-minute local run is the confirmation that the SHA you are about to merge actually builds.

## Dispatch rules (hard)
- Probe each profile once before launch: `hermes -p <p> chat -q "Reply with exactly: DISPATCH_OK" --oneshot -Q` — a profile with an invalid model ID still exits 0 and prints session metadata with NO answer; grep the output for the actual answer text.
- `-Q` (quiet) is required to get the answer on stdout; without it you get metadata only.
- Unique profile per concurrent node — two hermes sessions on the same profile contend. Plan the full item × node × profile matrix before launch; no profile reused concurrently.
- Reviewer and implementer are always different model families (policy); pick profiles accordingly.
- Scripts written via write_file are NOT executable: `chmod +x` before launch (first run dies exit 126 "permission denied").
- Foreground terminal blocks nohup/disown — launch chains with `terminal` `background=true`. For the long wait, a pgrep wait-loop with timeout 601 auto-promotes to a tracked background process that notifies on completion.
- Keep one spec phase/PR per task. Bundling adjacent spec work into one task (e.g. pay-copy into a routing PR) gets rejected as scope bleed — split the task rather than argue with the reviewer.
- **Phantom writes:** a file-writing node (TD, IM, FIX) can end its session with a message that *lists* the files it "wrote" when it actually executed no write calls — the final summary describes intent as completion. A chain commit-check aborts on this, but the guard that prevents the wasted cycle is in the BRIEF: require the node to include, in its FINAL message, literal `ls -la` output proving each claimed file exists with non-zero size PLUS `git status --short` showing exactly the files it changed. If a node phantoms (clean `git status` despite a file list), RE-RUN on a DIFFERENT profile with the verification gate added — do not trust the same profile to self-correct, and do not hand-write the files yourself to save a cycle (you'd be bypassing the independent-design property of that node).
- **Re-launch after a partial failure** without re-paying for an expensive gate: when a chain node aborts or a foreground launch gets SIGTERM'd mid-run, write a continuation script that re-verifies the completed gate's verdict is on record (grep the archived pass file for `CONTRACT: APPROVED` / the expected `VERDICT`) and then runs ONLY the remaining nodes. Confirm the worktree is still at the expected SHA + clean before the continuation's first node — a killed run can leave a foreign file behind.
- **Persist per-identity receipts before wide fan-out.** The manifest must record assignment, prompt hash, provider/model, attempts, final status and immutable artifact/revision hash; write each receipt atomically as soon as it validates. A large swarm that keeps results only in process memory loses proven coverage when the provider or parent process fails.
- **Recover provider-wide partial failures by failed identity, not by restarting the swarm.** First classify the common transport/auth/quota signature from stderr, count valid versus failed receipts in code, then dispatch only failed identities to an approved alternate provider. Preserve the original assignment and schema, log the substitution, independently validate the fallback receipt, and recheck the artifact hash. Do not count attempts, planned workers or invalid output as agents; the requested swarm count is satisfied only by that many valid identity receipts.
- **Probe structured-output compatibility before a fallback batch.** Run one failed identity end-to-end through the alternate CLI, remove schema metadata unsupported by that CLI only from the transport copy (keep the canonical validator unchanged), and launch the batch only after the returned envelope is parsed and validated. This avoids multiplying a schema-dialect mismatch across every fallback worker.

## Worktree hygiene (hard)
- Tool-enabled workers drag foreign uncommitted files into the worktree (stash pop, unrelated WIP). Before every review node: `git status --short` must be EMPTY. If dirty and the item's work is already committed: `git restore --source=HEAD --staged --worktree .` + `git clean -fd` (non-destructive; `reset --hard` may trigger a consent gate).
- A contaminated worktree makes the reviewer's full vitest/tsc gate red for reasons unrelated to the item and costs a FAIL. Clean before review, not after the verdict.
- Briefs must say "zero NEW errors vs base (diff the error set)" for tsc and item-scoped runs for vitest — repos carry pre-existing baseline failures that are not the item's fault.

## +G substitution (this machine)
The plan's premium judge (gpt-6-astra) is usually unauthenticated here. Use the declared cross-family alternate profile, name the substitution inside the judge prompt AND in the delivery to the operator (policy: substitutions are logged, never silent). Judge nodes: contract review BEFORE test design, premium acceptance AFTER review-PASS, acceptance bound to the exact revision SHA (a revision that differs from what the judge now sees is rejected).

## Money-path (+G) contract gate: a loop, not a one-shot

For a +G item (payments, irreversible writes), the PCON contract-judge node runs BEFORE test design and is the single highest-leverage gate in the build. Treat it as a REPEATABLE LOOP, not a single pass:

- **CHANGES_REQUIRED halts the chain** (the runner exits before TD). Revise the contract, then RE-RUN PCON. Do NOT proceed to TD on a CHANGES_REQUIRED, and do NOT skip the re-check because "I already fixed the things it found."
- **Contract rot is real: each revision round introduces new defects.** In a build that went through three PCON passes, pass 1 found ~11 defects and pass 2 found ~13 more (D1–D12) in the revisions THEMSELVES — a wrong file map, a seconds-vs-milliseconds unit bug, an open-shift omission, two competing count APIs in one money gate, and a scope change that would have taken down an unrelated existing phase. The new defects cluster exactly in the newly-edited prose. Re-run PCON after every revision until it says `CONTRACT: APPROVED`; APPROVED is the only exit to TD.
- **Point PCON at real data, not just the contract.** The judge re-measures the contract's quantitative claims against the live/cached source on every pass. Numbers you assert in the contract and then forbid TD from re-verifying (the standard "design from the contract" rule) become PERMANENT if wrong — so every quantitative claim in a +G contract should be one the judge can re-derive from a real fixture, and the judge must be told where that fixture lives.
- **A CHANGES_REQUIRED that names the exact verbatim edit is a gift.** When the judge supplies the precise replacement prose (not just "this is wrong"), apply it verbatim — re-wording it is how a defect re-introduces itself on the next pass.
- **The gate is doing its job when it is expensive.** Multiple CHANGES_REQUIRED rounds before a single line of payout code is written is the success case on a money path, not a failure to work around. Never route around it to save a cycle.
- **Cap the loop with a bounded final pass.** When a pass returns only mechanical verbatim edits (no new measurement) and the substance was already verified in prior passes, run the final PCON with an explicit bounded mandate: verify the N prescribed edits landed (cite the line each), and block ONLY on a NEW blocking defect the edits themselves introduced; list non-blocking nits in a separate section that does not trigger CHANGES_REQUIRED. This is a legitimate exit, not a weakened gate — the money-critical substance was re-measured every round. The final pass's halt must route to a human decision (revise-and-retry or manual review), not an automatic retry loop.
- **A premium-acceptance REJECT at a bound SHA on a test-only defect closes without a full chain re-run.** When PACC returns `ACCEPTANCE: REJECTED` with the defect confined to a test (not source) and it has independently confirmed the source correct on every money red line, the correct closure is minutes, not a node: apply the test-only fix, run the JUDGE'S OWN discriminating mutation to prove the fixed test now goes RED (revert the source byte-identical — verify with `git diff <bound-sha> -- <source>` empty), commit, and re-run ONLY the bound acceptance at the new SHA with the full attempt history + prior REJECT + the fix + the teeth-probe in the brief. The gate that found the defect re-accepts its own fix at the bound revision. Do NOT re-run TD/IM/RV for a test-only rejection, and do NOT hand-wave the acceptance — the bound-SHA sign-off is what a money path warrants.
- **A contract revision is a change to every artifact that cites it.** After revising the contract, sync ALL node briefs (TD/IM/RV/PCON) in the same step, before relaunch. Briefs that still assert the previous version's normative prose (an old signature, an old count rule, a permission the revision removed) make TD design tests against behavior the contract now forbids, and make the gate halt on phantom contradictions it then spends a round adjudicating. Grep the briefs for the version string AND each normative phrase the revision touched — the judge will catch a brief/contract mismatch and count it against you.
- **Archive per-pass review output.** A chain runner that `cp`s review output to a fixed filename overwrites the previous pass's record on every re-run — a lost pass-1 review forces later passes to reconstruct it from downstream references. `cp` each pass's output to a per-pass filename (`...-passN.md`) and `mv runs/<item>.log` to a per-pass name before re-launching the chain.

## Concurrent writers in a shared worktree (default-profile "continue" runs)
- A "continue" that points at a READY kanban task in a worktree may find the kanban worker profile (e.g. engineering-swarm-local-execution) ALREADY active in that same worktree — it commits under the operator's git identity (author line = the operator), so git log doesn't reveal who is writing.
- Detect BEFORE the first edit: `find <worktree>/app <worktree>/tests <worktree>/wiki -type f -newermt "-15 minutes"` + `git status --short` + `git log --oneline -2`. Non-deterministic test results (same file failing in different shapes run-to-run) = mid-write state, not a flaky suite.
- Protocol (the operator's decision, 2026-09-17): while the worker is active, the default profile does NOT commit and does NOT fight for the same fixes — it diagnoses, leaves a kanban comment listing exactly which fixes are on disk for the worker's commit, and backs out. The default profile's job is independent verification of the landed commit (full suite + static gate + `git show --name-only` content check) and the completion report. Verify, don't duplicate.
- mtime "stable" windows under ~2 minutes are not idle — worker iterations come in 1-3 minute bursts. Require stable ×2 consecutive checks plus a gate run before concluding the writer stalled; only take over remaining fixes if it is stalled AND the gate is still red.
- Re-read every file before each patch (the patch tool rejects stale reads) and expect scratch/diagnostic files you drop in a shared worktree to be deleted by the other writer — never depend on them surviving.
- Worker self-reports ("suite green", "committed") are self-reports: run the full suite yourself on the committed tree and confirm the commit's file list matches the task spec before closing the kanban task. Numbers may differ between runs (Feature-subset vs full suite) — reconcile the delta, don't just accept the worker's count.
- When verifying a landed commit, run the repo's EXACT pre-commit gate command (read the hook config first — husky → lint-staged), not an ad-hoc static analysis scoped to a hand-picked file list: a scoped run over files outside the analyzer's configured paths (e.g. test files) reports errors the gate does not count and burns time chasing phantom reds.
- `kanban_complete` failing with "unknown id, stale run, or already terminal" = a parallel session closed the task out-of-band. `kanban_show` to confirm the done state and what landed, verify the landed work yourself, and move on — do not retry the completion or treat the failure as your own error.
- Repo-specific gate + typing knowledge lives in per-repo skills (e.g. `internal-staffing-app-feature-delivery` for the HSS Laravel repo) — load that skill before judging green/red on a landed commit.

## Handoff
Deliver: per-item verdict (PASS/FAIL + findings), commit SHAs, worktree paths, substitution log, and the +H reminder that nothing is pushed and merge = prod deploy. the operator approves push/PR/merge explicitly, item by item.
